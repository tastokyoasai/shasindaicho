# 写真台帳アプリ（統合版）ver.2.23　仕様書

現場写真から看板を読み取り、看板ごとにグループ化して写真台帳（CSV／Excel）を出力し、写真のリネーム・フォルダ振り分けまで行う、単一HTMLのブラウザアプリです。従来の「写真台帳 照合アプリ（デジタル看板用）」と「手書き写し込み台帳アプリ（手書き看板用）」を1本に統合したものです。

---

## 1. 構成・動作環境

- **形態**：単一ファイル `index.html`（必要ライブラリを同梱／一部は同フォルダに配置）。サーバー不要、ブラウザ内で完結。
- **対象ブラウザ**：Google Chrome / Microsoft Edge（PC）。`showDirectoryPicker` が使える環境ではフォルダハンドルを再利用して振り分けまで行う。
- **オフライン**：QR検出・台帳出力・振り分けはオフラインで動作。高精度クラウドOCRのみネット接続が必要（未接続時は端末内OCRへ自動フォールバック）。
- **同梱ライブラリ**
  - `jsQR 1.4.0`（index.html にインライン）… QRデコード（基本）
  - `opencv.js`（@techstark/opencv-js 5.0）… QR検出の強化（傾き・小サイズ対策）。同フォルダの `./opencv.js` を最優先で読み込み、無ければCDN。
  - `Tesseract.js 5 + tessdata（jpn / eng）`… 端末内OCR（フォールバック）。同フォルダ優先、無ければCDN。
- **元データ非破壊**：取り込んだ写真は書き換えない。振り分けは「コピーしながらリネーム」。

## 2. 2つのモード

起動時オーバーレイで選択。`APP_MODE`（`'digital'` / `'writein'`）として保持し、`localStorage['sdc_app_mode']` に記録。ヘッダーの「🔀 モード変更」でいつでも切替。

| | 🖥 デジタル看板モード | ✍ 手書き看板モード |
|---|---|---|
| 由来 | 写真台帳 照合アプリ | 手書き写し込み台帳アプリ |
| QRの役割 | 看板データを丸ごと格納 | 「これは看板」の目印のみ |
| 中身の取得 | QRを解読して即反映 | 手書きを高精度OCR（クラウド／端末内）で読む |
| 一括手書きOCRボタン | 非表示 | 表示（「✍ 看板を手書きOCR」） |
| 取込直後の自動OCR | しない | 中継URL設定済みなら自動実行 |

### モードによるQR解釈（`kanbanFromQR`）
- **digital**：`parseKanbanQR(text)` のみ。`T1|…` 形式のデータQRだけを看板化（中身なしの「T1」単体は空看板）。それ以外のQRは看板扱いしない。OCR補完なし。
- **writein**：`T1|…` はデータを使用（区分の既定「調査」）。中身がちょうど `T1` の識別QRだけを「中身空の看板マーカー」として認識（**ver.2.2 で厳格化**。従来は任意QRを許容していたが、写真に写り込んだ無関係QRの誤認を防ぐため `T1` 限定に）。空看板は後で手書きOCRで補完。

高精度クラウドOCRは **ver.2.1 で両モードから利用可能**（`cloudEnabled()` のモード制限を撤廃）。デジタルモードでもQR不読の写真を「OCRでグループ作成」でクラウドOCR読み取り可能。

## 3. 看板QRのデータ形式

パイプ区切りの11項目。先頭は識別子 `T1` 固定。

```
T1|件名|調査区分|対象1|対象2|状況|方向|撮影日|撮影者|種別|備考
```

| 位置 | 項目 | 内部キー | 例 |
|---|---|---|---|
| 0 | 識別子 | ―（"T1"固定） | T1 |
| 1 | 件名 | kenmei | 古河市 東の門西の門城跡 |
| 2 | 調査区分 | kubun | 本調査 |
| 3 | 対象1（遺構番号） | t1 | SI01 |
| 4 | 対象2 | t2 | カマド |
| 5 | 状況 | joukyou | 完掘 |
| 6 | 方向 | houkou | 南 |
| 7 | 撮影日 | date | 2026-07-08 |
| 8 | 撮影者 | sha | 遠藤知成 |
| 9 | 種別 | shubetsu | 調査 |
| 10 | 備考 | biko | |

- **エスケープ**：項目内の半角 `|` は生成側（入力アプリ）で全角 `／` に置換。読取側は戻さない（利用者が打った全角スラッシュを保持するため）。
- 生成は現場スマホ用PWA「写しこみ看板 入力アプリ」（`/utusikomi/`、別デプロイ）。本統合版は読取側。

## 4. データモデル（主要オブジェクト）

- **photo**：`{ id, name, path, file/handle, dt, dtSource, thumb, qr(payload|null), kanban(parsed|null), failed, mark }`
- **state.groups[]**：`{ id, kanban, source('qr'|'ocr'|'manual'|…), qrPhotoId, photoIds[] }`
- **kanban**：`{ kenmei, kubun, t1, t2, joukyou, houkou, date, sha, shubetsu, biko }`
- **グループの種類（バッジ）**：QR（青）＝QR読取／OCR・要確認（紫）＝文字OCR／手動／追加（緑）＝差分取込で追加

## 5. 看板マスタ（選択肢）

`KANBAN_MASTERS`。編集画面でその場で追加・削除可能、`localStorage`（作業保存JSON）に保存。

- **prefix（対象1の遺構種別）**：P, SA, SB, SC, SD, SE, SF, SG, SH, SI, SJ, SK, SL, SM, SN, SO, SP, SS, ST, SU, SW, SX, SY, SZ, NR（番号桁数：P=3桁、他=2桁）
- **taishou2（対象2）**：カマド, 炉, P1, P2, P3, P4, P5, 貯蔵穴
- **joukyou（状況）**：検出, 完掘, 断面, 掘方完掘, 掘方断面, 出土状況, 検出状況, 設定状況, 復旧状況, 全景, 近景
- **shubetsu（種別）**：調査, 管理, 測量, 3D, 作業風景, メモ
- **方向（DIRS・固定）**：北西/北/北東・西/（対象）/東・南西/南/南東

## 6. 写真台帳（出力）

CSV／Excel（xlsx）で出力。写真1枚＝1行。列は入力シートと同じA〜M列。

`連番 | 調査区分 | 対象1 | 対象2 | 状況 | 方向 | 撮影日 | 撮影者 | 種別1 | 種別2 | フォルダ | ファイル名 | 備考`

- **種別1（I列）**：看板（写込）写真のみ「写込」。対象写真は空。
- **種別2（J列）**：振り分けに使う種別。対象写真の行で空欄のときは既定で **「調査」**（ver.2.1）。失敗指定は「失敗」。写込行は空のまま。
- **撮影日（G列）**：Excelでは日付セルとして出力（表示形式 `m/d`）。並び順はファイル名順（撮影順）。**ver.2.2**：撮影者(H列)への誤った日付書式付与を修正。印刷範囲を実データ行までに変更（従来は常に1001行）。ページ設定はA4横・幅合わせ。
- **CSV**：**ver.2.2**：先頭が `= + - @` で始まる値は先頭に `'` を付けて、Excelでの数式実行（数式インジェクション）を無害化。
- **Excel出力はExcelJSをCDNから読み込む**ため初回はネット接続が必要。CSVはオフラインで出力可。

## 7. 写真振り分け（コピー＆リネーム）

台帳に従い、元フォルダから保存先へコピーしつつリネーム・フォルダ分け。元写真は残す。

- **新ファイル名**：`〔対象1〕 〔対象2〕 〔状況〕（〔方向〕）_〔種別〕_〔元ファイル名〕.JPG`
  - 例：`SI13 カマド 完掘（南西）_調査_IMG_5624.JPG`（種別が空なら「調査」）
- **フォルダ**：
  - 種別が 調査／測量／メモ／空 … `調査区分／対象1`
  - それ以外の種別 … `調査区分／種別`
  - 調査区分が全行で空なら区分階層を作らない
- 種別「失敗」の行はスキップ。同名ファイルが既存ならスキップ（上書きしない）。使用不可文字 `\ / : * ? " < > | [ ]` は除去。
- **ver.2.2 のファイル安全化**：制御文字・末尾のドット/空白を除去、Windows予約名（CON, PRN, AUX, NUL, COM1〜9, LPT1〜9）は先頭に `_` を付与、ファイル名は200文字に抑制、重複判定は大文字小文字を無視。コピー元探索はサブフォルダの区切りを保持し、台帳が直下指定のときだけ直下へフォールバック（同名の別写真へ誤コピーしない）。

## 8. 高精度クラウドOCR（API・中継サーバー）

APIキーを公開HTMLに置かないため、中継サーバー（Cloudflare Workers＝`ocr-proxy/worker.js`）を経由してGeminiに画像を渡し、看板項目をJSONで受け取る。アプリ側は中継URLとON/OFFのみ保持（`localStorage['sdc_ocr_cloud'] = {url, on}`）。

### リクエスト（アプリ → 中継サーバー、POST JSON）
```json
{
  "image": "<base64 JPEG（先頭のdata:…は除く）>",
  "mime":  "image/jpeg",
  "hints": {
    "pref1":   ["P"],
    "pref2":   ["SA","SB", "... 遺構種別の候補"],
    "joukyou": ["掘方完掘","完掘","断面","全景","..."],
    "houkou":  ["北","南","東","西","北西","..."]
  }
}
```
- 画像は長辺1600pxのJPEG（品質0.85）に縮小して送信。

### レスポンス（中継サーバー → アプリ、JSON）
```json
{ "t1":"", "t2":"", "joukyou":"", "houkou":"", "date":"", "kenmei":"", "sha":"", "biko":"" }
```
- **対象1/2の読み取り方針（worker更新）**：`t1`/`t2` は「遺構番号コード（SI12・P001 等）」に加え、**コード形式でない自由記入（例:「試掘坑1」「カマド」「炉」）も表記どおり読み取る**。プロンプトで(A)コード／(B)自由記入の両方を明示。看板は「対象1・対象2」が1枠に並ぶ型と、独立した枠になっている型の両方に対応。
- サーバー側で正規化：`t1`/`t2` は **コード形式（英字1〜2＋数字）のときだけ**大文字化＋空白除去。自由記入は表記を変えず返す。`houkou` の末尾「から」を除去。
- 失敗・未読・レート制限(429)時はアプリが `null` を受け、端末内Tesseractへフォールバック（レート制限時は再試行せず中断）。

### 使用モデルの選択（worker.js）
- `GEMINI_MODEL` を設定すればそのモデルを固定使用。未設定時の既定候補は **`gemini-3.5-flash`（標準・精度優先）→ `gemini-3.5-flash-lite` → `gemini-2.5-flash-lite`** の順。
- **過負荷・不調への自動切替（ver.2.23）**：あるモデルが 503/500/502/429 を返す、または未提供(404)のときは**次の候補モデルへ自動フォールバック**。全候補が不調なら約0.7秒待って**もう1巡**再試行。全滅時のみ 503 を返し、アプリは端末内OCRへフォールバック。
- **思考オフ指定は 2.5系のみ**（`thinkingConfig.thinkingBudget=0`）。3.x系は既定が minimal のため送らない（送ると 400 BadRequest になるため）。
- **実際に使ったモデル名を返す**：成功レスポンスに `X-OCR-Model` ヘッダを付与（`Access-Control-Expose-Headers` で公開）。開発者ツールの Network → 該当リクエストのレスポンスヘッダで、現在どのモデルが使われているか確認できる。

### ver.2.2 の中継サーバー入力検査（worker.js）
- **オリジン制限**：`Origin` が `ALLOW_ORIGIN`（カンマ区切り可）に一致しなければ 403。CORSヘッダーも許可オリジンにのみ返す。
- **レート制限**：Cloudflare Rate Limiting binding `OCR_RATE_LIMITER`（既定 60回/分、キー＝オリジン＋IP）。超過は 429（`Retry-After: 60`）。binding未設定でも動作（その場合は無制限）。
- **入力上限／形式**：`Content-Type: application/json` 必須（違反415）。リクエスト10MB上限（超過413）。`mime` は `image/jpeg` のみ（違反415）。base64は8MB文字・復号6MB上限（超過413）、base64文字種検査（違反400）。
- **ヒント検査**：`hints.pref2/joukyou/houkou` はサーバー側の許可リストに載る値だけ採用（公開APIの入力をそのままプロンプトに渡さない）。

### 中継サーバーの環境変数（Cloudflare のシークレット／変数）
| 変数 | 必須 | 既定 | 説明 |
|---|---|---|---|
| `GEMINI_API_KEY` | ✔ | ― | Google AI Studio のAPIキー。`wrangler secret put` で登録（ファイルに書かない） |
| `GEMINI_MODEL` | | 実装既定 | 使用モデルを固定したいときに設定 |
| `ALLOW_ORIGIN` | ✔（**ver.2.2で必須**） | ― | 許可するオリジン（例：`https://ユーザー名.github.io`。末尾の `/` やパスは付けない）。カンマ区切りで複数可 |

デプロイ：`API_中継サーバー/` で
```
npx wrangler secret put GEMINI_API_KEY
npx wrangler secret put ALLOW_ORIGIN
npx wrangler deploy
```
→ 表示URLをアプリの「中継URL設定」に登録（中継URLは `https://` 必須）。レート制限 binding には Wrangler 4.36.0 以降が必要。`wrangler.toml` の `namespace_id` はアカウント内で一意な正整数（他 binding と重複する場合のみ変更）。

## 9. localStorage キー一覧

| キー | 内容 |
|---|---|
| `sdc_app_mode` | 選択中モード（'digital' / 'writein'） |
| `sdc_ocr_cloud` | 高精度OCRの `{ url, on }` |
| `shasin_workers` | QR並列処理数の設定 |

作業状態（グループ構成・看板内容・マスタ・失敗指定・写込指定）は「作業を保存」でJSON書き出し／「作業を復元」で読み込み。

### 保存先・復元元（フォルダ連携）
- **保存**：Chrome/Edge（https）で `showDirectoryPicker` によりフォルダ取り込みした場合、「作業を保存」は**その写真フォルダ直下に固定名 `写真台帳_作業状態.json` を上書き保存**（書き込み権限を都度要求）。ハンドルが無い環境（`file://`・複数ファイル選択・非対応ブラウザ）は従来どおり日時つきJSONをダウンロード。
- **復元**：「作業を復元」は、対応環境では**フォルダを選ぶだけ**で、フォルダ内の `写真台帳_作業状態.json` を読み込み→写真を取り込み→**保存時に未解析だった（新規の）写真だけを差分解析**して続行（内部的に `_pendingState` を設定して `importFromDirHandle` を実行）。フォルダに作業状態ファイルが無い／非対応環境では、JSONファイル選択の従来方式にフォールバック。
- **取り込み時の自動復元**：フォルダを「フォルダを選択」または**フォルダごとドラッグ＆ドロップ**で取り込んだとき、そのフォルダに `写真台帳_作業状態.json` があれば「復元して続きから再開しますか？」と確認し、承認すると復元＋差分解析を行う（`importFromDirHandle` 内で判定。ドロップは `getAsFileSystemHandle()` でディレクトリハンドルを取得するため、保存も復元もD&Dで可能）。個別ファイルのドロップ／複数ファイル選択ではハンドルが無く、保存はダウンロードになる。

### 作業状態JSONでの写真識別（ver.2.2）
- 写真は **相対パス（ルートフォルダ名を除いたサブフォルダ＋ファイル名）＝ `photoKey`** で識別。別サブフォルダの同名ファイルを取り違えない。
- 保存フィールド：`analyzedPhotoKeys` / `markedPhotoKeys`（写込）/ `failedPhotoKeys`（失敗）、各グループに `qrPhotoKey`・`photoKeys`（旧 `qrFile`・`files` も併存）。`version:"2.2"`。
- 旧JSON（ver.2.1以前・相対パス無し）互換：同名写真が1枚だけのときに限り復元（安全側）。ver.2.2で保存し直すと以後は相対パスで確実に区別。
- 写込・失敗指定は**取込前／取込後どちらの順で復元しても**正しく反映（ver.2.2で修正）。マスタは重複除去・各値100文字/最大200件にサニタイズ、グループ数20000超は読み込み拒否。
- 解析を**中断**した場合、未解析の写真は台帳へ混ぜない（差分取込時は既存分のみ復元、新規取込時はクリア）。

## 10. バージョン履歴

- **ver.2.23**（OCR安定化）：既定モデル順を ①gemini-3.5-flash → ②gemini-3.5-flash-lite → ③gemini-2.5-flash-lite に変更。中継サーバーで **503等の過負荷時に次モデルへ自動切替＋約0.7秒待って計2巡リトライ**。3.x系への `thinkingBudget` 送信をやめ **400 BadRequest を解消**（思考オフは2.5系のみ）。
- **ver.2.22**（マイナーチェンジ）：高精度OCRの既定モデル候補を ①gemini-3.5-flash-lite → ②gemini-2.5-flash-lite → ③gemini-3.5-flash の順に変更（Lite優先でコスト・無料枠を最適化、404時フォールバック）。使用モデル名を成功レスポンスの  ヘッダで返すように追加（現行モデルをNetworkで確認可能）。
- **ver.2.21**（マイナーチェンジ）：保存/復元のフォルダ連携（写真フォルダへ保存・フォルダ選択/ドラッグ&ドロップで自動復元＋未処理写真の差分解析）、状況の素直読み・対象1/2の自由記入OCR・思考オフによる高速化、デバッグ修正（コピー元サブフォルダの角括弧・復元の二重計上・ALLOW_ORIGIN未設定拒否）をまとめて反映。
- **ver.2.2（保存/復元のフォルダ連携）**：「作業を保存」で写真フォルダ内に固定名 `写真台帳_作業状態.json` を上書き保存（対応環境）。「作業を復元」でフォルダを選ぶだけで、状態復元＋未解析写真の差分解析までを一括実行。非対応環境は従来のダウンロード／JSON選択にフォールバック。
- **ver.2.2（デバッグ済み）**：コピー元サブフォルダの角括弧等をサニタイズせず実名で辿るよう修正。作業状態復元時の写真二重計上・不正グループを防止。中継サーバーは `ALLOW_ORIGIN` 未設定なら全要求を500拒否（フェイルクローズ）。
